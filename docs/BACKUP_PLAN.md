# خطّة النسخ الاحتياطي — منصّة حلقات البراك

> حالة: **خطّةٌ للمراجعة — لا تنفيذ بعد.**
> القيود الصارمة:
> - لا artifacts في المستودع العام
> - لا بيانات غير مشفَّرة
> - المفتاح في GitHub Secrets
> - الوجهة يحدّدها المدير قبل التنفيذ

---

## أ) المشكلة

Supabase Free tier يحتفظ بنسخةٍ احتياطيّة واحدة يوميّة لمدة يومٍ واحد فقط.
أيّ حذفٍ خاطئ أو عطلٍ في قاعدة البيانات قد لا يُستعاد إن اكتُشف بعد 24 ساعة.
لا Point-in-Time Recovery (PITR) على الخطّة المجانيّة.

---

## ب) المبدأ العام

```
Supabase Postgres (إنتاج)
    ↓  pg_dump مشفَّر (GPG symmetric)
GitHub Actions (workflow_dispatch أو cron)
    ↓  رفع الملفّ المشفَّر فقط
الوجهة (يحدّدها المدير)
```

الملفّ الوحيد الذي يغادر قاعدة البيانات هو تفريغ SQL مشفَّر.
لا plain-text، لا بيانات في السجلّات، لا artifacts علنيّة.

---

## ج) الخطوات المقترحة (بانتظار موافقة الوجهة)

### ١. مفتاح التشفير
- يُنشَأ مفتاح GPG symmetric مرّةً واحدة (AES-256).
- يُخزَّن في GitHub Secrets باسم `BACKUP_GPG_PASSPHRASE`.
- نسخةٌ ورقيّة (أو KeePass) تحفظها إدارة البراك — لا تُودَع في المستودع.

### ٢. سكربت النسخ (`.github/workflows/backup.yml`)
```yaml
# workflow_dispatch فقط — لا auto-cron حتى يوافق المدير على الوجهة.
on:
  workflow_dispatch:
    inputs:
      confirm:
        description: "اكتب BACKUP للتأكيد"
        required: true
```
الخطوات:
1. `pg_dump` على `DIRECT_URL` (Supabase Direct connection 5432).
2. تشفير الناتج: `gpg --symmetric --cipher-algo AES256 --batch --passphrase "$BACKUP_GPG_PASSPHRASE"`.
3. رفع الملفّ إلى الوجهة المختارة.
4. التحقّق: `gpg --decrypt … | head -5` (يجب أن يبدأ بـ`--`).
5. حذف الملفّ المؤقّت من الـrunner.

### ٣. الوجهات المحتملة (للمدير يختار)
| الوجهة | المزايا | العيوب |
|--------|---------|--------|
| Supabase Storage (bucket خاص) | نفس المنطقة، مجاني | يتطلّب service-role key إضافي |
| Google Drive (service account) | سهل الوصول | يحتاج إعداد OAuth service account |
| Cloudflare R2 | مجاني لأحجام صغيرة | يحتاج R2 token |
| GitHub Release (private repo) | بسيط | الحجم محدود (2GB) |

### ٤. جدول التشغيل (بعد اختيار الوجهة)
- **أسبوعياً:** السبت 03:00 مكة (UTC+3) — بعيداً عن أوقات الذروة.
- **يدوياً:** `workflow_dispatch` مع `confirm=BACKUP` قبل أي تغيير بيانات كبير.

### ٥. اختبار الاستعادة (شرط قبل الاعتماد)
قبل الاعتماد الرسميّ:
1. إنشاء قاعدة بيانات اختبار فارغة.
2. `gpg --decrypt backup.sql.gpg | psql <test-db>`.
3. التحقّق من عدد الصفوف في الجداول الرئيسيّة (`Student`, `DailySession`, `Enrollment`).
4. توثيق النتيجة في HANDOFF.md.

---

## د) ما لا يدخل الخطّة (مرفوض صراحةً)
- لا نسخ إلى مستودع عامّ أو مستودع خاصّ له وصول خارجي.
- لا plain-text SQL في أيّ artifact أو سجلّ.
- لا تخزين المفتاح في الكود أو CLAUDE.md أو أيّ ملفٍّ متتبَّع.
- لا توليد مفتاح جديد في كل تشغيل — مفتاحٌ واحدٌ ثابت (قابل للتدوير يدوياً).

---

## هـ) الخطوة التالية (تحتاج موافقة المدير)
1. المدير يختار **الوجهة** من الجدول أعلاه.
2. المدير يُنشئ المفتاح ويضعه في Secrets.
3. يُكتب workflow واقعيّ بناءً على الوجهة المختارة.
4. اختبار الاستعادة قبل الاعتماد.
